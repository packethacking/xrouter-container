# Bug `a526a4b04337` — NULL-pointer SIGSEGV at 0x4063e2

| field            | value                                          |
|------------------|------------------------------------------------|
| signal           | `SIGSEGV`                                      |
| RIP              | `0x4063e2`                                     |
| crashing insn    | `movzwl 0x2a(%rax),%eax`                       |
| RAX at crash     | `0x0`  ← NULL                                  |
| containing fn    | starts at `0x4061cb`                           |
| version          | 505c (other versions not yet retested)         |
| arch             | amd64 (tested)                                 |
| reached via      | AXUDP fuzzer; trigger not yet minimised        |
| state            | reproducible across cores from the same fuzzer run; possibly stateful |

## Summary

A pointer loaded from `[rbp-0x100]` is `NULL`, but the code at
`0x4063db` doesn't check before dereferencing it at offset `0x2A`. The
fault is a classic NULL-pointer read.

The function appears to be an **APRS packet formatter / decoder**.
Within ±0x300 of the function entry there are format strings
characteristic of the APRS spec's extended data: `" Alt: %d ft"`,
`" %d watts"`, `" feet"`, `"rectivity: %d deg"`, `", ch2=%d"`,
`"ch5=%d"` (PHG / DFS / telemetry encoders). The crash is reached
when one of the per-extension sub-records is missing but the
formatter walks into it anyway.

Distinct from `c0338d880e86`: same crash *shape* (`movzwl 0x??(%rax),%eax`)
but a different RIP, a different offset into the dereferenced struct
(0x2A vs 0x2), and `RAX = 0` (NULL) instead of a stale wild pointer.

## Reproducer (not yet minimised)

The AXUDP fuzzer found this with the regression-corpus seed plus
mutations. To re-encounter:

```sh

sleep 5
python3 fuzz/axudp-fuzz.py \
    --target 127.0.0.1:20900 \
    --health http://127.0.0.1:18900/ \
    --restart-cmd "fuzz/restart-target.sh repro 18900 20900" \
    --probe-every 300 --duration 300
```

A NULL-deref core matching signature `a526a4b04337` shows up within a
few minutes. Minimisation would require feeding the saved
`/work/xr/run-axudp/bugs/batch-*.txt` files into the existing
`fuzz/axudp-fuzz.py --replay` bisector once the trigger has been
isolated to a single batch.

## Suggested fix

Add a NULL check on the pointer loaded from `[rbp-0x100]` before the
two `movzwl 0x2?(%rax)` reads. Whatever upstream lookup returns this
pointer is sometimes returning NULL (table-miss?), and the caller
treats it as a valid record. The fix should either skip the formatting
step on NULL or have the upstream lookup return a sentinel non-NULL
"unknown" record.

## Severity

- DoS today: reachable through the AXUDP/AX.25 frame parser. With
  `LEARN=1` (the common "ad-hoc" AXUDP config) this is reachable from
  anywhere on the Internet that can send a UDP packet to the AXUDP
  port — and on RF, from anyone in range.
- Not a memory corruption primitive: NULL-deref reads are not RCE
  candidates by themselves. Severity: DoS, MEDIUM-HIGH.
