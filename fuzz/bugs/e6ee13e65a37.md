# Bug `e6ee13e65a37` — SIGABRT in `raise()`-from-somewhere at 0x63ac9c

| field            | value                                          |
|------------------|------------------------------------------------|
| signal           | `SIGABRT`                                      |
| RIP              | `0x63ac9c`                                     |
| crashing insn    | `mov %eax,%r13d` (immediately after `syscall` for `tgkill`) |
| version range    | 505c (latest); presumed others, not retested  |
| arch reach       | amd64 (tested); other arches likely identical  |
| reachable from   | HTTP, AXUDP, NetRom (and probably more)        |
| state            | stateful — does NOT reproduce by replaying the recorded trigger frame in isolation |
| exploitability   | DoS today; the abort is via the stack-canary / fortify path so the underlying issue is almost certainly a memory-corruption bug (stack overflow, heap corruption, fortify-detected `strcpy` overflow). Treat as a candidate for further exploitability analysis. |

## Summary

**This is a stack buffer overflow** in an HTTP request-handling
function. A long `Authorization: Basic …` header (~200 bytes of
attacker-supplied base64) is copied into a fixed 272-byte stack buffer
without a length check. The stack canary catches the smash and
`__stack_chk_fail` calls `abort()`. **With the canary** the impact is
DoS; **without it** (older builds / different compiler flags) this is
a classic stack-smashing RCE primitive.

## Live backtrace (gdb-attached, SIGABRT caught)

```
#0  0x63ac9c   inside raise() — right after the tgkill syscall
#1  0x6170a6   return into the raise() wrapper at 0x617090
#2  0x4017b6   site that calls raise(SIGABRT) — likely __stack_chk_fail's local helper
#3  0x633276
#4  0x69bbda   __stack_chk_fail (entry at 0x69bb90 + offset)
#5  0x69bba6
#6  0x471b03   return address INSIDE the vulnerable function
                (function entry 0x47151e, called from 0x47c2ee)
#7-#17 0x4141414141414141   <-- the stack frame is overwritten with
#18    0x0000004141414141   "AAAAAAAA" — the same 'A' bytes the
                            fuzzer sent in `Authorization: Basic AAA…`
```

The `0x4141414141414141` repeats are the literal `A` (0x41) bytes from
the long `Authorization` header. They overwrote the saved RBP, the
return address, and at least eight more 8-byte slots above the
canary, confirming the bug is a straightforward unbounded copy from
the header buffer onto the stack.

## Vulnerable function

```
0x47151e  <fn_start>: endbr64 / push rbp / mov rsp,rbp / sub $0x200,rsp
                 ; — 512-byte stack frame, with a 272-byte (0x110)
                 ; child buffer at -0x110(%rbp) that gets repeatedly
                 ; appended to via 0x52f8ab (a strcat-like helper).
...
0x471a05  lea -0x110(%rbp),%rax        ; append into local buffer
0x471a0c  mov %rax,%rdi
0x471a0f  call 0x52f8ab                 ; strcat-like, no length check
...
0x471a3f  mov -0x1c0(%rbp),%rax         ; pointer to a caller-supplied buffer
0x471a42  mov %rax,%rdi
0x471a47  call 0x62d790                 ; presumed Auth-decode / copy
...
0x471afc  je   0x471b03                 ; canary OK?
0x471afe  call 0x69bb90                 ; <-- __stack_chk_fail
0x471b03  leave; ret                    ; (only reached if canary intact)
```

Sole caller: `0x47c2ee` (which in turn is called from three HTTP
request-dispatcher sites at `0x47e4cf`, `0x47e613`, `0x47eb27`).

## Reproducer (deterministic via PRNG seed)

The bug is fired during HTTP fuzzing about every ~300-600 frames and
during NetRom fuzzing every ~20k-100k frames. The deterministic
reproduction:

```sh
# Boot a fresh target instance
fuzz/restart-target.sh repro 18900 20900
sleep 5

# Reproduce the HTTP-triggered abort. Same PRNG seed -> same input
# sequence on any host.
python3 fuzz/http-fuzz.py \
    --name repro --http-port 18900 --udp-port 20900 \
    --probe-every 200 --duration 60 --seed 127256512
```

Expected: at least one `[!] NEW BUG e6ee13e65a37 ... SIGABRT` line in
the output, and the target restarts. The same SHA-1 signature appears
for every reproduction.

## Suggested fix

The leaf bug is in the function at `0x47151e`. Replace the unbounded
string-concat loop into the 272-byte local buffer with a bounded
variant (`snprintf` / `strlcpy` with the buffer size). The
`Authorization`, `Host`, and `Cookie` header parsers should each
clamp the value length they pass downstream — RFC-compliant values
for these are well under 200 bytes; reject anything longer with `400
Bad Request` rather than copying it.

A grep of the binary for callers of the strcat-like helper at
`0x52f8ab` (654 call sites) will reveal other call paths that may
have the same shape; the HTTP path is just where the fuzzer reached it
first.

Until a fix lands, mitigations any operator can apply:

- Block external access to `HTTPPORT` (LAN-only firewall). The bug is
  pre-auth on this port — anyone who can reach it can crash the node.
- Disable any reverse-proxy that forwards `Authorization` / `Cookie`
  / `Host` headers verbatim.

## Severity

- DoS today: trivially achievable from anywhere on the network that
  can reach the HTTP port. Bug fires within ~400 mutated requests.
- Potential RCE: the stack frame is being smashed by attacker-supplied
  bytes (proven — the `A`s appear in the saved-RBP slot). With the
  stack canary, the program calls `abort()` instead of jumping to
  attacker-controlled return addresses. A binary compiled without
  `-fstack-protector` (or where the canary is leaked first) would be
  exploitable for control-flow hijack. **Treat as HIGH severity even
  with the canary in place** — the underlying memory corruption is a
  one-bug-fix away from being weaponisable, and the canary-protected
  abort can still be used for persistent DoS.
